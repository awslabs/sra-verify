# Requirements Document

## Introduction

The scanner's three-tier error model assigns each tier one job. A client catches the AWS exception and returns a value describing what happened. A check reads that value and decides whether the control is absent (FAIL) or could not be evaluated (ERROR). The orchestrator catches whatever escapes and degrades one row rather than the scan. The middle tier is the one that matters to a consumer, because FAIL and ERROR are not two shades of the same thing: FAIL asserts that AWS was asked and the control is not in place, while ERROR admits the question went unanswered.

That model is broken at the first tier. Of the 144 exception handlers across the 18 service clients, 100 — in 11 clients: `accessanalyzer`, `auditmanager`, `cloudtrail`, `config`, `ec2`, `guardduty`, `inspector`, `macie`, `s3`, `securityhub`, `securitylake` — discard the error and return a bare `{}`, `[]`, `None`, or a bare boolean. (The AST audit in `.tmp/audit_clients.py` reports 103, because it counts return statements rather than handlers and misses the one handler in `auditmanager` that has no return statement at all and falls off the end as `None`. Either figure is a floor.) A further 13 handlers in `firewallmanager` and `waf` return an error result that carries the message but drops the code, and one handler in `guardduty` returns a third shape, the string `"ERROR:{code}:{message}"`, which its caller parses by prefix and then caches as `None`. In every one of these cases the code and message are gone before the check runs, so the check cannot distinguish a disabled service from a denied permission from an unreachable endpoint, and the branch it lands on is whichever one the author wrote for "no data".

Where that branch resolves to `failed()`, an undetermined state is published as an established negative. Twenty-five check modules do so with wording that admits the uncertainty — "Unable to retrieve detector details", "Failed to retrieve Macie organization configuration", "status could not be determined". An unknown further number do so with wording that does not: `SRA-S3-01` through `-04` report "No public access block configuration found" whether the account has no configuration or the role lacks `s3:GetAccountPublicAccessBlock`, because `S3Client.get_public_access_block` maps both `NoSuchPublicAccessBlockConfiguration` and `AccessDenied` to `{}`; `SRA-INSPECTOR-01` through `-04` report "Inspector state status: NOT_ENABLED" on any client failure; `SRA-ACCESSANALYZER-01` reports "No IAM Access Analyzer configured" when `list_analyzers` returned `[]` on `AccessDenied`. These rows are indistinguishable from genuine findings in the CSV. Only the build log can tell them apart.

A second defect compounds it. Only 4 of 18 clients catch any member of the `BotoCoreError` family, and 7 catch nothing but `ClientError`, so a transport failure — a timeout, a DNS failure, an unreachable regional endpoint — escapes `execute()` and the orchestrator converts the whole check into a single synthetic ERROR row. Every row the check had already yielded for the Regions that worked is discarded with the generator frame. A third: 72 base-class accessors across the 18 service base classes write the client result into the per-scan cache; 66 do so without testing it for an error, 4 test only partially, and 2 cache the error result deliberately. One transient failure is replayed for the rest of the scan.

Measured against the 2026-09-12 organization scan of 13 accounts and 4 Regions, 3063 rows (`sraverify-consolidated-20260912_183733.csv`): 112 FAIL rows carry an `ActualValue` that reads as an inability to determine, and a further 8 rows assert that a Security Lake subscriber is absent while the same build log records `AccessDenied` on the call that would have listed it. 120 rows, 3.9% of the report, state a finding the scan never established, and the dashboards count each of them as a finding. That 120 is a floor: it counts the rows whose wording confesses, and none of the rows whose wording does not.

The fix is already prototyped. `MacieClient.get_classification_export_configuration` and `WAFClient.list_services` were brought to the intended contract in commit `bdad609`, each paired with a discriminator on its service base class, and both were validated against the live organization. This feature generalizes those two reference implementations across the remaining clients and makes the contract enforceable rather than conventional.

One further concern rides along. The scanner is also a library behind an MCP server that speaks JSON-RPC over stdio, so any byte the library writes to stdout corrupts the transport. Today stdout is clean for the library entry point, `SRAVerify.run_checks`, but only by convention: `core/logging.py` routes every logger to stderr, and the 17 `print()` calls in the package all sit in the CLI's `main()`, the banner, the progress bar, and the inventory listings, none of which `run_checks` reaches unless asked. Nothing tests that. This feature adds three new diagnostic paths — the client guard's `error` log, the availability lookup's `warning`, the cache backstop's `warning` — and a sweep that touches every client and base module, which is exactly the kind of change that lets a stray `print()` in. Requirement 8 makes the convention a contract so that this feature, and the next one, cannot regress it.

The verdict-preserving property is the point of the exercise and also its main risk. Where a control genuinely is absent, the row must stay FAIL and only its stated reason may improve; that is what the Macie precedent demonstrated, holding 52 FAIL rows on each of `SRA-MACIE-03` and `-04` at FAIL while replacing "Failed to retrieve Macie classification export configuration" with the reason AWS actually gave. Where the control was never evaluated, the row must become ERROR, and the FAIL count must drop by exactly that many. Neither property can be established from the CSV alone, which is why the acceptance gate in Requirement 6 reconciles every changed row against the build log.

## Superseded during implementation

Three things in this document were decided differently once the migration was
under way. The criteria below are otherwise unchanged and still normative; where
one was amended it says so inline.

**1. No shared `call_aws` guard.** The design specified one helper that ran a
closure and wrote the two `except` clauses once for all 92 client methods. After
four methods were migrated it was rejected: a reader of `client.py` should see
the error handling at the call site, not a lambda handed to a function in another
module. Every client method now carries its own plain `try`/`except`.

**2. The error result is built by `AWSClient.aws_error(e)`, which takes only the
exception.** The first replacement for `call_aws` was a module-level
`sentinel_from(e, operation="GetDetector", region=self.region)`. Both keyword
arguments were then removed. `operation=` came out because botocore sets
`operation_name` on every `ClientError`, so a hand-typed literal was redundant
where it agreed and silently wrong where it did not — the one value in the client
tier no test could defend. `region=` came out because every client already stores
its Region. What remains is a base class in `core/aws_client.py` holding `region`,
`ctx`, and `aws_error`, so the handler is byte-identical in all 92 methods and
there is nothing per-call-site to get wrong.

A consequence: a `BotoCoreError` carries no operation, because the request never
completed. Those error results carry `UNKNOWN_OPERATION = "Request"` rather than
reintroducing a parameter for that one case.

**3. `ClientContractError` was never shipped.** It existed only for the shared
guard's non-mapping check. See its glossary entry and criteria 1.5 and 7.3.

**Terminology.** What this document originally called a *sentinel* is now an
**error result**, in the code and here. A sentinel is conventionally a placeholder
standing in for absence; this value is the opposite — a structured record of what
AWS said. The old name was inherited from the design it replaced, where the
alternative really was a bare `{}`.

## Glossary

### Domain terms

- **Client**: The `<Service>Client` class in `services/<svc>/client.py`. Wraps raw boto3 calls for one AWS service. Never raises to its caller.
- **Error result**: The value a client returns in place of a successful response when the underlying AWS call failed, of the form `{"Error": {"Code": <str>, "Message": <str>, "Operation": <str>}}`. The `Operation` key is new in this feature; the two reference implementations emit `Code` and `Message` only.
- **Named-key success dict**: The value a client returns on success, and the value a Base_Accessor passes through unchanged: a dict whose top-level keys are the AWS response member names, e.g. `{"Roots": [...]}` from `organizations:ListRoots`, `{"subscribers": [...]}` from `securitylake:ListSubscribers`. Paginated results are merged under the same key. The presence or absence of `"Error"` is the only test that separates a success dict from an error result.
- **Error-erasing handler**: An exception handler in a client that returns a value carrying neither the error code nor the error message — a bare `{}`, `[]`, `None`, `True`, or `False`, whether by an explicit `return` or by falling off the end of the handler. 100 exist across 11 clients.
- **Code-dropping handler**: An exception handler that returns `{"Error": {"Message": ...}}` with no `Code`. 13 exist across `firewallmanager` (2) and `waf` (11).
- **Transport failure**: A failure to complete an AWS call that produces no AWS error code, raised by botocore as a member of the `BotoCoreError` family rather than as `ClientError`. The guard catches the whole family; the three subclasses `EndpointConnectionError`, `ConnectTimeoutError`, and `ReadTimeoutError` are additionally named in `TRANSPORT_ERROR_CODES` so a check can pick network-oriented remediation wording for them.
- **Programming defect**: Any exception raised inside a client's guarded call that is neither `ClientError` nor `BotoCoreError` — `AttributeError`, `KeyError`, `TypeError`, `IndexError`. Not an AWS outcome. Propagates unchanged to the Scan_Orchestrator, whose synthetic row is its report.
- **`ClientContractError`**: *Superseded — never shipped.* Specified as a new `SRAVerifyError` subclass raised by the shared guard when a client's success path returned a non-mapping. The shared guard was dropped during implementation (see "Superseded during implementation" below), and with no guard there is no single place to make the check. The Contract_Tests assert the success-path shape directly instead, which catches the same defect before it ships rather than at scan time.
- **Adapter**: A per-method test fixture declaring how to call a client method or base accessor (arguments), which boto3 client attribute and operation it uses, and what success response shape it reads. Fixture data for the Contract_Tests, paired with a reflection-equality assertion so it cannot lag the code.
- **Reference tree / candidate tree**: The two commits an Acceptance_Gate run compares — the last commit before a batch and the batch itself — scanned in the same window so that environmental drift between scans is not mistaken for a code change.
- **Invocation stderr**: The stderr stream of one `sraverify` process, i.e. one account at one account type, captured to its own file by the buildspec. The unit of log evidence for the gate.
- **Semantic error code**: An AWS error code whose meaning, *for the operation that produced it*, is "the thing is not configured" rather than "the request could not be served". Examples already classified as such somewhere in the tree: `AWSOrganizationsNotInUseException` from `DescribeOrganization`; `ResourceNotFoundException` from `macie2:GetClassificationExportConfiguration`, `shield:GetSubscriptionState`, `account:GetAlternateContact`, and `fms:GetAdminAccount`; `PolicyTypeNotEnabledException` from `organizations:ListPolicies`; `NoSuchEntity` from `iam:GetRole`; `WAFNonexistentItemException` from `wafv2:GetWebACLForResource`; `InvalidAccessException` with message containing `not subscribed to AWS Security Hub`; `UnauthorizedException` from any `securitylake` operation; `BadRequestException` from `guardduty:DescribeOrganizationConfiguration` but not from `guardduty:ListOrganizationAdminAccounts`; `NoSuchPublicAccessBlockConfiguration` from `s3control:GetPublicAccessBlock`. A semantic error code resolves to FAIL; every other error resolves to ERROR.
- **Discriminator**: The per-service declaration of which `(operation, error code)` pairs mean "not configured", and the single shared predicate that reads it. `MacieCheck.is_macie_disabled_error` is the reference implementation in spirit; it predates the operation dimension and is an imperative predicate rather than a table.
- **Overloaded error code**: An AWS error code returned for both a semantic condition and an access failure, so that the code alone cannot classify the error. `macie2` returns `AccessDeniedException` both when Macie is disabled in a Region and when the caller lacks the API permission; the message `Macie is not enabled` separates them. `securityhub` returns `InvalidAccessException` both when Security Hub is not subscribed and for other access problems; the message `not subscribed to AWS Security Hub` separates them.
- **Probe**: A client method whose success-path return is a bare `bool` answering "is the service present / enabled here?" — `AccessAnalyzerClient.is_access_analyzer_available` and `SecurityLakeClient.is_security_lake_enabled`. A probe has no place to carry an error result, so its failure path is always erasing.
- **Base accessor**: A cached typed method on a `<Service>Check` base class that calls a client method and stores the result on the per-scan context under the service `NAMESPACE`.
- **No-client condition**: The state in which a Base_Accessor finds no `<Service>Client` wrapper registered for the requested Region, because `_setup_clients` did not create one. Neither a success nor an AWS failure; an undetermined state.
- **Regional availability**: Whether an AWS service has an endpoint in a given Region, as recorded in the endpoint data bundled with botocore. Determined offline, with no AWS call and no credentials.
- **Verdict**: The `Status` of a finding — `PASS`, `FAIL`, or `ERROR`.
- **Undetermined state**: A condition in which the scanner did not establish whether a control is in place. Its only correct verdict is ERROR.
- **Confessing FAIL**: A FAIL row whose `ActualValue` wording admits an undetermined state ("Unable to retrieve", "could not be determined"). Detectable from the CSV by pattern. 112 in the baseline scan.
- **Masked FAIL**: A FAIL row whose `ActualValue` asserts absence in confident wording but whose underlying client call failed. Not detectable from the CSV; detectable only by reconciling against the build log. The 8 Security Lake rows are the measured instance; the S3, Inspector, and Access Analyzer paths named in the Introduction are the known unmeasured ones.
- **Library entry point**: `SRAVerify.run_checks()` and every code path it reaches, called with `show_progress=False` (the default). This is what the MCP server invokes. `main()`, `print_banner`, `ScanProgress`, and the `--list-checks` / `--list-services` paths are the CLI surface and are not part of it.
- **Library module**: Any module under `core/`, `services/`, or `utils/outputs.py`. `main.py`, `utils/banner.py`, and `utils/progress.py` are CLI modules. `__init__.py` is a library module; its docstring example uses `print()` and is exempt because a docstring is not executed.
- **Diagnostic output**: Anything a library module emits that is not a return value: log records, warnings, or writes to a stream. The contract is that all of it goes through the `sraverify` logger, which `core/logging.py` binds to stderr.

### System names used in acceptance criteria

- **Service_Client**: Any `<Service>Client` class, considered collectively as the set of 18.
- **Client_Contract**: The required shape of every client method's return value on both the success and the failure path.
- **Transport_Guard**: The exception handling in a client that contains the `BotoCoreError` family and the final catch-all.
- **Base_Accessor**: Any cached typed accessor on a `<Service>Check` base class, considered collectively.
- **Cache_Discipline**: The rule governing what a Base_Accessor may write to the per-scan cache.
- **Discriminator**: The per-service predicate classifying an `(operation, error result)` pair as semantic or not.
- **Check_Catalog**: The 158 check modules, considered as one deliverable.
- **Availability_Lookup**: The offline regional-availability helper.
- **Scan_Orchestrator**: The `SRAVerify.run_checks` loop and its per-check guard. Gains one `info`-level structured line per check, `check_done check_id=… rows=…`, for gate attribution; otherwise unchanged.
- **Acceptance_Gate**: The before/after CSV comparison, reconciled against the build log, that admits or rejects each service's migration.
- **Contract_Tests**: The automated tests that hold the contract after this feature ships.
- **Library_Entry_Point**: `SRAVerify.run_checks()` as defined in the glossary, considered as the surface the MCP server consumes.
- **Stdout_Contract**: The rule that no library module writes to `sys.stdout`, and that every diagnostic emitted by a library module goes through the `sraverify` logger.
- **Reference_Implementation**: Four pieces of the current tree, each demonstrating one part of the contract. `OrganizationsClient` (5 of 5 methods return a named-key success dict or a `Code`+`Message` error result, paginated, the shape `structure.md` documents as canonical). `IAM_Client.list_users` (the most complete hand-written shape in the tree: `ClientError`, then a transport tuple, then a catch-all, every path yielding an error result — a reference for the *error result*, not for the catch-all, which Requirement 2 criterion 2 removes). `MacieClient.get_classification_export_configuration` with `MacieCheck.is_macie_disabled_error` (an overloaded code classified by message; the accessor refuses to cache the error result). `WAFClient.list_services` with `WAFCheck.region_supports_service` (transport codes named as a constant; offline regional availability with partition derivation and fail-open on an unknown service id).

## Out of Scope

1. **Re-deriving the FAIL-versus-ERROR judgement centrally.** The mapping is a function of the pair (operation, error code), not of service alone: `BadRequestException` is an ERROR through `ListOrganizationAdminAccounts` and a FAIL through `DescribeOrganizationConfiguration`. This feature makes the error *available* to the check and requires the check to classify it through a per-service Discriminator that takes the operation as an input, but there is no cross-service table. Accepted cost: a reviewer auditing one service's classification reads that service's Discriminator; there is no single place to read all of them.

2. **Changing any PASS verdict.** This feature touches only the paths reached when an AWS call fails or when no client exists for a Region. The expectation is that a row which passes today passes afterward with the same `ActualValue`. That is a hypothesis the Acceptance_Gate tests (Requirement 6 criterion 5), not a fact this document asserts. Accepted cost: pre-existing defects on success paths — a set joined into an `ActualValue` in `sra_macie_07`, an unstable `Region` label in `sra_securityincidentresponse_01`, the hardcoded `us-east-1` in `sra_firewallmanager_01` — are untouched and remain live, including in files this feature edits for their error path.

3. **Retry or backoff.** Distinguishing a transient failure from a permanent one is not the same problem as reporting it honestly, and the bounded `botocore.config.Config` already owns retries. Accepted cost: a throttled call yields an ERROR row on the first attempt past the botocore retry budget rather than being retried at the check layer.

4. **Restructuring the region loop.** No `evaluate(region)` hook. The regional-availability guard is added per check that needs it, in the check body, ahead of the AWS call. Accepted cost: the guard is duplicated in each check whose service has uneven regional coverage, and a check that needs one but does not have one is not detectable by the type system.

5. **Changing the orchestrator's handling of a mid-generator exception.** `run_checks` materializes `list(check.execute())` inside its guard, so a check that raises after yielding contributes one synthetic ERROR row and nothing else. `main.py` records this as a deliberate decision, and this feature relies on it: once no client raises for an AWS outcome, the synthetic row becomes evidence of a programming defect — in a check, a base class, or a client — rather than an expected outcome, and that signal is worth more than the partial rows. Accepted cost: a programming error anywhere in the three tiers still costs that check's whole output for the account. The one edit `main.py` receives is a single `info`-level `check_done` log line per check, for gate attribution.

5a. **Adding pagination where it is missing.** Five client methods read only the first page of a paginated operation (Requirement 1 criterion 13 lists them). Fixing that is correct and out of scope, because it changes the success path's call count and can change verdicts by surfacing resources the first page omitted, and Out of Scope 2 promises no PASS moves. Accepted cost: the first-page truncation persists, and a large organization's `inspector2:ListAccounts` still sees at most 20 accounts.

5b. **Deterministic replay fixtures for the gate.** Recording every AWS response from a baseline scan and replaying it against both trees would make the gate environment-independent. It is the right long-term answer and it is a cassette system, which is a project in itself. This feature instead runs both trees in the same window (Requirement 6 criterion 1) and re-runs single-sided ERRORs (criterion 14). Accepted cost: a resource that changes during the two-scan window can still produce an unexplained difference, which the gate reports and a human adjudicates from the archived evidence.

6. **`securityincidentresponse` region resolution.** That base class declares no `NAMESPACE` and pins `self.regions[0]` in three accessors, producing an unstable row key. It is a known defect, it is adjacent, and folding it in would mix a Region-labelling change into a verdict-correctness change and make the Acceptance_Gate unreadable. Deferred. Its client's six handlers already return a `Code`+`Message` error result; its base's `_discover_memberships` sweep and `get_organization_accounts` do fall under Requirement 3 and Requirement 4, and only those.

7. **The `IAMCheck._validate_metadata` dead method, the four per-client `get_account_id()` methods that duplicate `ScanContext.get_account_info()`, and the stale developer README.** Unrelated cleanups. The `get_account_id()` duplicates are noted because they will be touched by the sweep (each has an erasing handler); bringing them to the contract is in scope, deleting them in favour of the context is not.

8. **Repairing the MCP server.** `sra-verify-mcp/awslabs/sraverify_mcp_server/server.py` lines 293–295 call `f.get('Status')` on the objects `run_checks()` returns, which have been `Finding` instances with no `.get()` since the check-contract merge on 2026-09-14. Every `run_check` tool call raises `AttributeError` today. That is a defect in the other repository, flagged by the check-contract design as a required follow-up and still open. It is a prerequisite for validating this feature through the MCP path, not part of this feature. Accepted cost: until it lands, the MCP server cannot be used to exercise any batch's after-state, and the Stdout_Contract is held by tests in this repository alone.

9. **Making the CLI surface quiet.** `main()`, `print_banner`, `ScanProgress`, and the inventory listings write to stdout on purpose; the buildspec and the operator read them there, and exit-code test `test_exit_codes_scan.py` asserts the summary appears. The Stdout_Contract is scoped to library modules and the Library_Entry_Point. Accepted cost: a consumer that calls `main()` rather than `run_checks()` gets stdout output, which is the documented behaviour.

## Requirements

### Requirement 1: Uniform client error result

**User Story:** As a check author, I want every client method to hand me the AWS error code and message when a call fails, so that I can classify the failure instead of guessing from an absence of data.

#### Acceptance Criteria

1. WHEN an AWS call inside a Service_Client method fails with a `ClientError` or any `BotoCoreError`, THE Client_Contract SHALL require that method to return `{"Error": {"Code": <string>, "Message": <string>, "Operation": <string>}}` and no other failure shape, where each of the three values is a `str` that is non-empty after stripping whitespace, and `Operation` is the AWS operation name as botocore reports it (`ListSubscribers`, `GetDetector`), so that the check and the Discriminator can name the operation without the Base_Accessor having to pass it separately. The error result test `is_error()` SHALL require `Error` to be a mapping whose `Code`, `Message`, and `Operation` are each a `str` that is non-blank after stripping, so that a malformed or half-built value is neither treated as an error result nor passed downstream as a success; and the Contract_Tests SHALL exercise every missing-key, blank, and wrong-type case for each of the three fields.
2. THE Client_Contract SHALL require the `Code` value to be the AWS error code as reported by botocore where one exists, and the exception's type name where none exists, so that a transport failure is classifiable by the same mechanism as a `ClientError`.
3. THE Client_Contract SHALL require the `Message` value to be non-empty, and to be the AWS error message from `e.response["Error"]["Message"]` where one exists rather than `str(e)`, so that a Discriminator matching on message text sees the same string across services.
4. THE Client_Contract SHALL prohibit a failure path from returning `{}`, `[]`, `None`, `True`, `False`, a string, or falling off the end of a handler, because none of those carries the information the check layer needs and each is indistinguishable from a legitimate empty result.
5. THE Client_Contract SHALL require every Service_Client method to return a dict on every non-raising path: a Named-key success dict on success and the error result on failure. A method whose success path today returns an extracted list, scalar, or bool SHALL return the AWS response under its response member name instead. THE Base_Accessor SHALL return that dict unchanged, so the dict is uniform at every tier; extraction of the list or scalar SHALL happen only after the error test, in the check body or in a pure helper that takes a success dict and is never handed an accessor's raw return. A Base_Accessor that must read a value from one response to make a second call (GuardDuty's detector ID) MAY do so internally after its own error test, and SHALL return the first call's error result unchanged when that test fails. This is the shape the `organizations`, `iam`, `shield`, and `securityincidentresponse` checks already consume. It makes `"Error" in result` the only test separating success from failure at every layer, and it removes the hazard of a truthy, iterable error result dict flowing into a branch written for a list. IF a Service_Client method's success path produces a value that is not a mapping, THEN the Contract_Tests SHALL fail for that method, because that is a defect in the client and not an AWS outcome. *(Amended: originally a runtime raise of `ClientContractError` from the shared guard. With the guard dropped there is no single place to make the check at runtime, and a per-method `isinstance` would be 92 copies of a test the suite already runs once per method. Property 4 asserts every method returns a `Mapping` on its success path, so the defect is caught before it ships rather than converted into a synthetic row at scan time.)*
6. THE Client_Contract SHALL prohibit a Service_Client from classifying an error code. WHERE a client today maps a semantic error code to an empty or success-shaped value — `securitylake` on `ResourceNotFoundException`, `s3` on `NoSuchPublicAccessBlockConfiguration`, `firewallmanager` on `ResourceNotFoundException`, `waf` on `WAFNonexistentItemException`, `securityhub` returning `None` on `InvalidAccessException` — THE Client_Contract SHALL require that method to return the error result carrying the code, and the Discriminator to make the judgement, because a client that answers the FAIL-versus-ERROR question has made it at the wrong tier and without the operation context.
7. THE Client_Contract SHALL prohibit a Service_Client method from returning a bare `bool`. A Probe SHALL be replaced by a named-key dict from the underlying operation, with the boolean question answered in the Base_Accessor, or by the Availability_Lookup where the question is regional presence (Requirement 5 criterion 8).
8. IF a Service_Client method catches an exception, THEN THE Client_Contract SHALL require it to log at `error` level exactly one structured line of the form `aws_call_failed operation=<Operation> region=<Region> code=<Code> message=<JSON-encoded Message>`, where `message` is the last field and its value is `json.dumps(Message)` — quoted, with embedded newlines, carriage returns, and quotes escaped — so that an AWS message containing a newline cannot break the one-line promise, and so that the Acceptance_Gate can parse the line by field rather than by prose. `Operation`, `Region`, and `Code` contain no whitespace by construction (AWS operation names, Region names, and error codes never do; exception type names never do), so they need no quoting.
9. THE Client_Contract SHALL require every Service_Client method to return normally for every `ClientError` and every `BotoCoreError`, and SHALL require any other exception raised inside the guarded call — `AttributeError`, `KeyError`, `TypeError`, and their kin — to propagate unchanged, because such an exception is a programming defect in the client and the Scan_Orchestrator's synthetic row is the correct report of a defect. A guard that converted it into an error result would let a broken client produce a plausible ERROR row per Region indefinitely.
10. THE Client_Contract SHALL apply to every exception handler in every Service_Client: the 100 error-erasing handlers across the 11 clients named in the Introduction, the 13 code-dropping handlers across `firewallmanager` and `waf`, the string-returning handler in `GuardDutyClient.get_detector_id`, and the return-less handler in `AuditManagerClient.get_account_status`. The 30 handlers that already return a `Code`+`Message` error result SHALL be brought to criterion 3 where they use `str(e)` for `Message` (`shield`, `account`, `auditmanager`, `guardduty`) and to criterion 8 where they log below `error` (`shield` logs at debug). The 44 bare `except Exception` handlers across 10 clients SHALL be removed, not narrowed in place, because criterion 9 forbids what they do.
11. THE Client_Contract SHALL define client construction as outside the guard and outside the error result model: `ScanContext.get_client()` calls `boto3.Session.client()`, which reads bundled endpoint data and issues no network call, so its failure is deterministic — an unknown service id, a malformed Region name, a broken botocore install — and is a defect that the Scan_Orchestrator's per-check guard already reports as a synthetic row through `initialize()`. A Service_Client SHALL call `ctx.get_client()` only in its `__init__`, assigning the result to an instance attribute, and nowhere else: not in a method body and not inside the closure passed to the guard. Today `cloudtrail`, `config`, `ec2`, and `macie` acquire an `sts` client inside `get_account_id`, `securitylake` acquires `sqs` inside `get_sqs_queue_encryption`, and `shield` acquires `lambda`, `cloudfront`, `wafv2`, and `cloudwatch` inside methods; each moves to `__init__`. Constructor-only acquisition costs nothing measurable — `ScanContext.get_client` caches by `(service, Region)` so the `sts` client is built once per scan however many wrappers ask for it — and it is what makes two other things true: a construction failure cannot be mistaken for a `BotoCoreError` and turned into an error result by the guard, and every `<attribute>.<method>(...)` call in a client module can be attributed to exactly one service by reading `__init__`. A Region with no endpoint for the service SHALL NOT be treated as a construction failure, because botocore constructs such a client successfully and fails only at call time, where the Transport_Guard catches it.
12. THE Client_Contract SHALL require the operation name passed to the guard to be a string literal at the call site. `util/generate_iam_policy.py` SHALL be updated to derive the IAM action set by binding each `self.<attribute> = ctx.get_client('<service>', ...)` in a client's `__init__` to its service, then collecting every `self.<attribute>.<method>(` and `self.<attribute>.get_paginator('<method>')` in that module under that service — the same receiver-attribution the generator already performs for `session.client(...)`, which no client has used since the scan-context refactor, so its current output is derived from nothing and "generated policy unchanged" is not evidence. The `call_aws` operation literal is a cross-check (it must equal the PascalCase form of the receiver method), not the attribution mechanism, because a literal alone cannot say which of `WAFClient`'s nine clients issued it. The generator's tests SHALL assert the exact action set for at least `WAFClient` (nine services) and `ShieldClient` (five), so that multi-service attribution is proven rather than assumed.
13. THE Client_Contract SHALL NOT add pagination to any Service_Client method that lacks it today, because doing so changes the success path's call count and may change verdicts by surfacing resources the first page omitted; the design SHALL record each pagination gap it finds (`inspector2:ListAccounts`, `config:DescribeConfigurationAggregators`, `config:DescribeConfigurationAggregatorSourcesStatus`, `shield:ListProtections`, `securitylake:GetDataLakeSources`) as a deferred correction.

### Requirement 2: Transport failure containment

**User Story:** As an operator, I want an unreachable endpoint in one Region to cost me one row, so that a DNS failure does not silently delete the results the scan already produced for every other Region.

#### Acceptance Criteria

1. THE Transport_Guard SHALL catch `BotoCoreError` — the whole family, not the three transport subclasses alone — in every Service_Client method that issues an AWS call, in addition to `ClientError`, because `NoCredentialsError`, `UnknownServiceError`, `EndpointResolutionError`, and `ProxyConnectionError` are all "the SDK could not complete the call" and none carries an AWS error code, and enumerating three of them leaves the rest to propagate.
2. THE Transport_Guard SHALL catch nothing beyond `ClientError` and `BotoCoreError`. There SHALL be no `except Exception` in any Service_Client, so that a programming defect inside the guarded call propagates to the Scan_Orchestrator (Requirement 1 criterion 9) and a traceback reaches the build log through the orchestrator's `exc_info=True` rather than being flattened into an error result `Code`.
3. WHEN the Transport_Guard catches a `BotoCoreError`, THE Client_Contract SHALL return the error result with `Code` set to the exception's type name and `Message` set to `str(e)`, and the three transport subclass names SHALL remain enumerated in `TRANSPORT_ERROR_CODES` so that a check can choose network-oriented remediation wording for them.
4. THE Transport_Guard SHALL NOT catch `BaseException`, so that an interrupted scan does not produce a report that looks complete.
5. THE Check_Catalog SHALL produce no finding whose `ActualValue` begins with the Scan_Orchestrator's synthetic-row prefix `Error running SRA-`, other than a finding produced by the Scan_Orchestrator's own guard, and a full-organization scan SHALL produce zero such rows for any supported configuration, so that the synthetic ERROR row becomes evidence of a defect — in a check, a base class, or a client — rather than an expected outcome. A row that names a `BotoCoreError` subclass in its `ActualValue` because the check classified it (Requirement 4 criterion 8) is not a synthetic row and is not covered by this criterion; a row that names `AttributeError`, `KeyError`, `TypeError`, or any other non-AWS exception type is by construction synthetic, because criterion 2 leaves no other path by which those names reach a cell.
6. WHERE a Service_Client already imports a member of the `BotoCoreError` family, THE Transport_Guard SHALL additionally require that the handler return the error result, because `securitylake` demonstrates that catching a transport failure and erasing it are independent defects: its seven `(BotoCoreError, ClientError)` handlers classify the exception for logging in `_log_aws_failure` and then return `[]`, `{}`, `None`, or `False`.
7. THE Transport_Guard SHALL name the transport exception types once, as a module-level constant in `core/` that both clients and Discriminators import, replacing the `TRANSPORT_ERROR_CODES` constant currently local to `services/waf/client.py`, so that a check testing for a transport code and a client producing one cannot drift.
8. THE Check_Catalog SHALL contain no direct SDK access: no check module SHALL call `self.session.client(...)`, `boto3.client(...)`, `boto3.Session(...)`, or `self._ctx.get_client(...)`, because a call made outside a Service_Client is outside the Transport_Guard and outside the error result model. `sra_accessanalyzer_02` is the one module that does so today (`self.session.client('organizations')` inside a bare `except` that resolves to `failed()`); it SHALL route through `AccessAnalyzerClient.get_delegated_admin` instead. THE Contract_Tests SHALL additionally assert, by AST, that in every Service_Client module `get_client(` is called only inside `__init__` (Requirement 1 criterion 11), so that the constructor-only rule is enforced and not documented.

### Requirement 3: Failures are never cached

**User Story:** As an operator, I want a transient failure in one Region to be retried rather than replayed, so that one throttled call does not turn into a Region's worth of identical rows.

#### Acceptance Criteria

1. IF a client method returns an error result, THEN THE Cache_Discipline SHALL require the calling Base_Accessor to leave its cache slot unwritten and return the error result to its caller.
2. THE Cache_Discipline SHALL permit a Base_Accessor to write to the per-scan cache only a value that is not an error result.
3. THE Cache_Discipline SHALL apply to every Base_Accessor that calls `_set`: 72 methods across 82 call sites by manual inspection of the 18 service base classes, of which 66 write unguarded, 4 guard partially (`GuardDutyCheck.get_detector_id`, `SecurityHubCheck.get_enabled_standards`, `SecurityHubCheck.get_enabled_products_for_import`, `SecurityIncidentResponseCheck._discover_memberships`), and 2 already guard fully (`MacieCheck.get_classification_export_configuration`, `WAFCheck.get_apprunner_services`). Each SHALL be confirmed individually, because the AST audit flags 64 and the manual count 72, and the difference is helpers such as `_seed_empty` inside `SecurityLakeCheck._prime_region_log_sources` that write without receiving a client result.
4. THE Cache_Discipline SHALL reverse the deliberate failure-caching at the sites that do it on purpose, and the design SHALL name each: `IAMCheck.list_users` ("Cache both success and error responses"), `SecurityHubCheck.get_organization` (builds the error result in its own `except` and caches it), `GuardDutyCheck.get_detector_id` (parses the `ERROR:` string and caches `None`), and the `SecurityLakeCheck` accessors `is_security_lake_enabled`, `get_subscribers`, `get_organization_configuration`, `get_sqs_queue_encryption`, `get_data_lake_sources`, and `_prime_region_log_sources` ("Preserve pre-refactor behavior: cache False on error").
5. WHERE two checks call the same Base_Accessor and the underlying call fails, THE Cache_Discipline SHALL accept that the AWS call is issued once per calling check rather than once per scan, as the observed cost of not caching a failure.
6. THE Cache_Discipline SHALL NOT change which successful responses are cached, under which namespace, or under which keys, so that a scan issues the same number of AWS calls as it does today on every path where nothing fails. The cached *value* does change for every accessor whose client previously extracted a list or scalar: the cache now holds the named-key success dict (Requirement 1 criterion 5). That is a change in representation, not in what is fetched or when.
7. WHEN a Base_Accessor encounters the No-client condition, THE Cache_Discipline SHALL require it to return the error result with `Code` equal to `NoClient` and a `Message` naming the Region, and SHALL NOT write to the cache, matching the shape `AuditManagerCheck` already uses, so that a missing wrapper is reported as the undetermined state it is rather than as an empty result. `SecurityLakeCheck.get_subscribers`, `get_sqs_queue_encryption`, and `get_data_lake_sources`, which today cache `[]` or `None` on no-client, SHALL stop.

### Requirement 4: The check layer classifies every error

**User Story:** As a consumer of the report, I want a FAIL to mean AWS told us the control is absent, so that I never investigate a misconfiguration that the scan did not actually observe.

#### Acceptance Criteria

1. WHEN a Base_Accessor returns a dict to a check, THE Check_Catalog SHALL require that check to test for the `Error` key before reading any success-path field, and SHALL prohibit truthiness tests (`if not result`) as the sole guard, because an error result dict is truthy.
2. IF an error result carries a semantic error code for the operation that produced it, THEN THE Check_Catalog SHALL require the check to yield a FAIL naming the condition AWS reported.
3. IF an error result carries any other code, including every transport code and `NoClient`, THEN THE Check_Catalog SHALL require the check to yield an ERROR whose remediation addresses the scan environment rather than the control.
4. THE Discriminator SHALL be declared once per service, on that service's base class, as a declarative table keyed by operation name and error code, read by a single `is_not_configured(error: dict) -> bool` implementation on `SecurityCheck` that takes the error result's `Error` sub-dict (which carries `Operation`), and that table SHALL be the only place that service's semantic error codes are enumerated, so that two checks reading the same error result from the same operation cannot classify it differently, so that the same code from two operations can be classified differently where the operations warrant it, and so that the Contract_Tests can enumerate every service's semantic codes by reading the table rather than by exercising a predicate.
5. WHERE an AWS error code is overloaded, THE Discriminator SHALL classify using the error message in addition to the code, and SHALL document at its definition why the code alone is insufficient.
6. THE Discriminator SHALL classify an unrecognized error code, or a recognized code arriving from an operation it is not declared for, as non-semantic, so that a code AWS introduces later produces an honest ERROR rather than a fabricated FAIL.
6a. THE Discriminator SHALL carry, for every `(operation, code[, message])` entry, a required non-blank `evidence` field — a structural part of the entry, validated at construction, not a comment — citing either the AWS API reference page that documents the code's meaning for that operation or a build-log line from a controlled account observed to produce it, because a table entry converts an ERROR into a FAIL and an entry asserted without evidence can turn a genuine permission failure into a fabricated finding. An entry whose evidence is a placeholder SHALL fail the Contract_Tests as soon as no adapter of that service remains in the pending set (Requirement 7 criterion 10a), not only when the whole migration completes. Entries seeded from existing inline classifications that carry no evidence today — `securitylake` `UnauthorizedException` (asserted only by `_log_aws_failure`'s docstring) and `auditmanager` `AccessDeniedException` with "Please complete AWS Audit Manager setup" (the code is inferred from the client's handler, not observed) — SHALL be confirmed against a live account in their batch before the table entry is committed, and SHALL be omitted from the table (so the code resolves to ERROR) if they cannot be.
7. THE Check_Catalog SHALL contain no `failed()` call whose `ActualValue` matches any of the confessing patterns, case-insensitively: `failed to (retrieve|get|fetch|access|determine|check)`, `unable to (retrieve|get|fetch|access|determine|check)`, `could not (be )?(determine|determined|retrieve|retrieved|access|accessed)`, `error (retrieving|getting|fetching|checking|accessing|determining)`, or an interpolated `str(e)` / exception object. This resolves the 25 modules holding one today: `sra_guardduty_02` through `_12` and `_17` through `_19` (14), `sra_macie_01`, `_02`, `_07`, `_08`, `_09`, `_10` (6), `sra_securityhub_02`, `sra_config_01`, `sra_config_02`, `sra_cloudtrail_11`, and `sra_accessanalyzer_02`.
8. WHERE a check reports an undetermined state, THE Check_Catalog SHALL require the row's `ActualValue` to identify the failed operation and the error code, so that the report distinguishes a permission gap from an unreachable endpoint without reference to the build log. A shared remediation helper for such rows SHALL NOT compose an IAM action string from `meta.service`, because display names such as `IAM Access Analyzer` and `FirewallManager` are not IAM prefixes and a fabricated action is worse than none; it SHALL name the operation and leave the action to the check, or use an explicit IAM prefix the service base class declares.
9. WHERE a check today emits a masked FAIL — confident wording on an erased error — THE Check_Catalog SHALL route the error result through the Discriminator like any other, and the design SHALL name the known sites: `sra_s3_01` through `_04`, `sra_inspector_01` through `_04`, `sra_accessanalyzer_01`, `sra_securitylake_16` and `_17`, and every check consuming a `GuardDutyCheck.get_detector_id` that returned `None`. These are not detectable by criterion 7 and are the reason the Acceptance_Gate reconciles against the build log.
10. WHERE this feature changes an existing verdict on a path that is not an erased-error path — an ERROR-to-FAIL flip because the code is semantic (`sra_securityincidentresponse_04` reporting "no active memberships" as ERROR is the known instance), or a FAIL-to-ERROR flip because the branch reported an undetermined state as FAIL for a reason other than an erased error (the `sra_cloudtrail_08`/`_09`/`_10` unparseable-timestamp branches under criterion 11) — THE Check_Catalog SHALL list each such intended flip in the design by check ID and branch, so that the Acceptance_Gate reviewer can distinguish it from a regression.
11. THE Check_Catalog SHALL prohibit any `except` clause inside `execute()`, not only one that resolves to `failed()`, because after Requirement 2 a client raises only for a programming defect and a check that catches one is hiding it from the Scan_Orchestrator's guard. Seven modules hold one today, in two kinds. Four wrap a client or accessor call and are replaced outright by the error result path: `sra_accessanalyzer_02` (bare `except` → `failed()`), `sra_accessanalyzer_03` and `_04` (bare `except` → `error()`), and `sra_config_09` (bare `except` around `describe_configuration_aggregator_sources_status` → `error()`). Three wrap timestamp parsing of a value already retrieved — `sra_cloudtrail_08`, `_09`, `_10` catch `(ValueError, TypeError)` and yield `failed()` — and SHALL move the parse into a pure helper on `CloudTrailCheck` that returns `None` on failure, with the check yielding `error()` for `None`, because a value the scanner cannot interpret is an undetermined state and not evidence that the control is absent. That is a FAIL-to-ERROR change on a branch not observed to fire in the baseline scan, and it SHALL be listed under criterion 10 so the Acceptance_Gate reviewer recognizes it.
12. WHEN every Base_Accessor a check calls returns a non-semantic error result, THE Check_Catalog SHALL require that check to yield only ERROR findings — no PASS, no FAIL — each with an `ActualValue` meeting criterion 8. This is the behavioural form of criterion 1 and is testable for every check in the catalog without a manifest, by patching every accessor on the check's service base class to return an error result and running `execute()`.

### Requirement 5: A Region without an endpoint produces no row

**User Story:** As a consumer of the report, I want the absence of a service in a Region to be silent, so that the ERROR column carries only conditions worth acting on.

#### Acceptance Criteria

1. THE Availability_Lookup SHALL determine whether a named AWS service has an endpoint in a named Region using the endpoint data bundled with botocore, issuing no AWS call and requiring no credentials, with the signature `service_available_in_region(service_id: str, region: str) -> bool` and no session parameter, because the bundled endpoint data is process-global and a session argument that the implementation ignored would mislead a reader into thinking the answer depends on it. Every statement that can raise, including construction of the botocore session used to read the data, SHALL be inside the fail-open handler, so that criterion 4 holds for the whole function and not for part of it.
2. THE Availability_Lookup SHALL derive the partition from the Region rather than defaulting to the commercial partition, so that a GovCloud or China scan is not measured against the commercial Region list.
3. IF the service identifier passed to the Availability_Lookup is not a service botocore recognizes, THEN THE Availability_Lookup SHALL report the service as available and SHALL log at `warning` level, because the underlying lookup answers "supported nowhere" for an unrecognized name and a mis-typed identifier would otherwise disable a check in every Region without a diagnostic.
4. IF the Availability_Lookup cannot determine availability for any other reason, THEN THE Availability_Lookup SHALL report the service as available, so that a lookup defect costs an honest ERROR row rather than silent suppression.
5. WHERE a service has no endpoint in a Region, THE Check_Catalog SHALL require a check consulting that service to yield no finding for that Region and to issue no AWS call for it.
6. THE Check_Catalog SHALL NOT infer the absence of a service from a transport failure, because a Region with no endpoint and a Region behind a broken network raise the same exception.
7. THE Availability_Lookup SHALL be applied only to services whose regional coverage is uneven, and each application SHALL name the boto3 service identifier as a literal at the call site, so that the set of checks relying on Region suppression is greppable. Measured against botocore 1.43.6's bundled endpoint data for the `aws` partition (34 Regions), the candidate set is `apprunner` (11 of 34; already applied in `sra_waf_06`), `auditmanager` (12), `securitylake` (17), `amplify` (20), `macie2` (22), `appsync` (31), and `inspector2` (32). `accessanalyzer` is rejected: it has an endpoint in all 34 Regions, so the lookup would never suppress a row. `s3control` (29 of 34) is rejected: the S3 checks emit a single `global` row from `regions[0]` and never iterate Regions. `security-ir` is rejected: it is a home-Region-pinned service whose `ListMemberships` returns an empty list rather than failing in other Regions, so endpoint presence does not predict where its data lives.
8. WHERE botocore's regional lookup answers an empty list for a recognized service — because the service is non-regionalized and declares only a partition endpoint (`shield`, `account`, `organizations`, `iam`, `cloudfront` all answer `[]` for the `aws` partition while listing `aws-global` when non-regional endpoints are included), or because botocore ships no endpoint data for it at all (`security-ir` answers `[]` under both readings in botocore 1.43.6) — THE Availability_Lookup SHALL report the service as available in every Region, because an empty list means "not resolvable per Region", never "reachable from nowhere". This is the one input on which a fail-closed reading would be wrong for every Region at once, and it makes the rule a single test: a service is unavailable in a Region only when the regional list is non-empty and does not contain that Region.
9. THE Availability_Lookup SHALL NOT be consulted by `AccessAnalyzerCheck`; instead the live probe in `AccessAnalyzerCheck._setup_clients`, which today issues `accessanalyzer:ListAnalyzers` once per Region to decide whether to register a client, treats `AccessDeniedException` as "available", and swallows every other exception, SHALL be deleted and that base SHALL register a client for every Region unconditionally, as every other regional base does. The probe's one AWS call per Region goes away with it.
10. THE Availability_Lookup SHALL live in `core/`, shared by every service, replacing `WAFCheck.region_supports_service`, which SHALL delegate to it or be removed.
11. THE Availability_Lookup SHALL cache its answer per `(service identifier, Region)` for the life of the process, because the bundled endpoint data cannot change while the process runs and a full-organization scan asks the same question once per check per Region.

### Requirement 6: Catalog migration and acceptance gate

**User Story:** As a maintainer, I want the sweep validated against a real organization before it lands, so that a change intended to correct 120 rows is proven not to have moved the other 2943.

#### Acceptance Criteria

1. THE Acceptance_Gate SHALL compare two full-organization scans of the same accounts and Regions run back to back: one from the last commit before the batch (the **reference tree**) and one from the batch (the **candidate tree**), so that a difference between them is far more likely attributable to the code than to a resource that changed between 2026-09-12 and the day of the gate. Same-window scanning narrows the drift window from weeks to minutes; it does not close it, and a resource that changes between the two runs will still produce an unexplained difference. THE Acceptance_Gate SHALL therefore treat any unexplained difference as a rejection to be re-run (criterion 14), never as noise to be waved through. The 2026-09-12 scan remains the reference for the aggregate counts in criteria 9 and 11 and is not the row-level comparand.
2. THE Acceptance_Gate SHALL match rows as multisets grouped by the logical key (account ID, account type, Region, check ID), because a check may legitimately emit several rows under one logical key — `SRA-WAF-02` emits one per load balancer, `SRA-SHIELD-03` one per protection — and a dictionary keyed that way would overwrite them while a join would cross-multiply them. Within each group, rows SHALL first be paired exactly on the full 16-cell tuple; remaining rows SHALL then be paired on `ResourceId` where that `ResourceId` is non-blank and occurs exactly once among the remaining rows on each side; remaining rows on each side SHALL then be sorted by the tuple (`ResourceId`, `Status`, `ActualValue`, `Remediation`) and paired in that order by admitted transition (criteria 4–6), each reference row consuming at most one candidate row and each candidate row being consumed at most once; any row left unpaired on either side SHALL be reported as added or removed and judged under criterion 7. Every step is deterministic given the two inputs, so two runs of the gate on the same artefacts SHALL produce the same pairing.
3. THE Acceptance_Gate SHALL obtain its evidence from two structured sources and no free-text inference: (a) one stderr file per `sraverify` invocation, so per account and account type, captured by the buildspec (`2-sraverify-codebuild-deploy.yaml`) and uploaded beside that invocation's CSV, so that the `parallel` fan-out cannot interleave five accounts' diagnostics into one stream; and (b) two structured log lines emitted by the scanner — `aws_call_failed operation=… region=… code=… message=…` at `error` level from the client guard (Requirement 1 criterion 8), and `check_done check_id=… rows=…` at `info` level from the Scan_Orchestrator after each check — so that every `aws_call_failed` line is attributable to exactly one check by position, because execution within one invocation is single-threaded. Both lines are emitted through the `sraverify` logger and are therefore on stderr; the buildspec SHALL NOT pass `--debug`, and the `sraverify` logger's default level of `INFO` SHALL be what makes `check_done` visible.
4. THE Acceptance_Gate SHALL admit a FAIL-to-ERROR transition only where the candidate invocation's stderr, between the previous `check_done` and this check's `check_done`, records an `aws_call_failed` line for that Region whose `operation` is one the check depends on and whose `code` the Discriminator classifies as non-semantic. The check-to-operation dependency SHALL be derived statically — check module → accessor names called → base accessor → client method → operation literal (Requirement 1 criterion 12) — by a helper in `util/gate.py`, not maintained by hand.
5. THE Acceptance_Gate SHALL admit an `ActualValue` change on a row whose verdict is unchanged where the row is an ERROR and the new value matches `^\S+ failed: \S+: `, or the row is a FAIL and the check is one whose discriminated FAIL wording changed in this batch (listed in the batch's gate notes); and SHALL admit a `ResourceId` change only alongside an admitted verdict or `ActualValue` change on the same paired row.
6. THE Acceptance_Gate SHALL reject any PASS-to-FAIL, PASS-to-ERROR, FAIL-to-PASS, or ERROR-to-PASS transition, and SHALL reject any ERROR-to-FAIL transition not listed under Requirement 4 criterion 10.
7. THE Acceptance_Gate SHALL admit an added row only where the reference invocation's stderr records, for that check, a synthetic-row condition (a traceback or an `Error running` line) — rows recovered from a generator that a transport failure aborted — and SHALL admit a removed row only where the Availability_Lookup answers `False` for that check's service in that Region. Every other added or removed row SHALL reject.
8. THE Acceptance_Gate SHALL reject any change to the 16 column names or their order, and SHALL reject any difference at all in rows whose `Service` belongs to a service not in the batch, because those rows exercise the shared code (`call_aws`, the `_set` backstop, `is_not_configured`) and a difference there is a regression in it.
9. THE Acceptance_Gate SHALL require the count of confessing FAIL rows in the candidate scan to be non-increasing per batch and zero once the batch containing the last of the 25 modules has landed, against 112 in the 2026-09-12 scan. This criterion is necessary and not sufficient: it detects the rows whose wording admits uncertainty and none of the masked FAILs.
10. THE Acceptance_Gate SHALL require, for every FAIL row in the candidate scan from a check named in Requirement 4 criterion 9, that the candidate invocation's stderr for that account records, in that check's window, no `aws_call_failed` line for that Region on an operation the check depends on, or only lines whose `code` the Discriminator classifies as semantic. This is the criterion that detects a masked FAIL.
11. THE Acceptance_Gate SHALL require that every check ID in the registry produces at least one row in the candidate scan, against 158 of 158 in the 2026-09-12 scan, and that the candidate scan contains zero rows whose `ActualValue` begins `Error running SRA-`.
12. THE Acceptance_Gate SHALL be evaluated per batch, filtered by the `Service` column to the batch's services for criteria 2–7 and 9–10, and unfiltered for criteria 8 and 11, so that the sweep lands incrementally and the operational cost is two scans per batch.
13. THE Acceptance_Gate SHALL archive, for every gate run, both scans' consolidated CSVs and per-invocation stderr files (produced by `util/local_scan.py`; task 12's CodeBuild capture was withdrawn rather than shipped in a public template) with their SHA-256 digests in the findings bucket under a batch-named prefix, and SHALL record the reference and candidate commit hashes and the digests in the batch's gate notes, kept with those artefacts rather than committed — their digests refer to CSVs that are not in the repository, so committing them would promise an auditability they cannot deliver — with the verdict and totals recorded in `tasks.md` instead. The 2026-09-12 CSV and its CloudWatch log export SHALL be archived the same way before Batch 1, because today the CSV is gitignored at the repo root and the log lives only in CloudWatch.
14. THE Acceptance_Gate SHALL re-run any check whose row differs between the two scans without an admitted explanation — an ERROR on exactly one side, an unpaired row that neither criterion 7 clause admits, a cell change that no criterion admits — for that account only, against both trees, before counting it as a rejection, so that a throttled call or a resource that changed between the two runs is not mistaken for a regression; SHALL count it as a rejection if the re-run reproduces it; and SHALL record every re-run and its outcome in the gate notes.
15. THE Acceptance_Gate SHALL be implemented as `util/gate.py`, committed, taking the two CSV paths and the two stderr directories, exiting non-zero on any rejection with the offending logical keys and rows listed, and SHALL itself be tested against a synthetic pair of CSVs and stderr sets covering every admitted and every rejected transition, so that the gate is not the one untested component in the change.

### Requirement 7: The contract is enforced rather than documented

**User Story:** As a maintainer, I want the next client method that erases an error to fail a test, so that this sweep does not decay the way the conventions it replaces did.

#### Acceptance Criteria

1. THE Contract_Tests SHALL assert, for every Service_Client method that issues an AWS call, that a simulated `ClientError` produces a return value matching the error result shape with a non-empty `Code` equal to the simulated code and a non-empty `Message` equal to the simulated message.
2. THE Contract_Tests SHALL assert, for every Service_Client method that issues an AWS call, that a simulated `EndpointConnectionError` produces an error result whose `Code` is `EndpointConnectionError`, and that a simulated `NoCredentialsError` produces one whose `Code` is `NoCredentialsError`, so that the guard is shown to cover the `BotoCoreError` family and not only the three transport subclasses.
3. THE Contract_Tests SHALL assert, for every Service_Client method that issues an AWS call, that a simulated `RuntimeError` raised by the boto3 call **propagates** unchanged, and that the method's success path returns a `Mapping`, so that Requirement 1 criterion 9 and the non-mapping-return defect are both held. *(Amended: the second half originally asserted that a closure returning a list raises `ClientContractError`. There are no closures and no `ClientContractError`; Property 4's `isinstance(result, Mapping)` assertion per method is what now holds it.)*
4. THE Contract_Tests SHALL assert, for every Service_Client method, that a successful boto3 response of the shape that method reads produces a dict that does not satisfy `is_error`, so that Requirement 1 criterion 5 holds on the success path as well as the failure path.
4a. THE Contract_Tests SHALL drive every Service_Client method through a per-method adapter — the arguments to call it with, the boto3 client attribute it uses, the operation name it passes to the guard, and the success response or paginator page shape it reads — declared in one table per service in the test module, because placeholder arguments and empty responses cannot exercise a method that branches on an ARN's service segment or indexes a required response member. THE Contract_Tests SHALL assert that the set of methods discovered by reflection equals the set of adapters declared, in both directions, so that the table cannot lag the code: a new method without an adapter fails, and an adapter for a deleted method fails.
5. THE Contract_Tests SHALL assert, for every Base_Accessor, that an error result returned by its client leaves the per-scan cache unwritten and that a second call re-issues the underlying AWS call; and that the No-client condition produces a `NoClient` error result and likewise leaves the cache unwritten; each driven through the same adapter mechanism as criterion 4a, with the accessor's arguments and the client method it delegates to declared once per accessor and reflection-equality asserted the same way.
5a. THE Contract_Tests SHALL assert Requirement 4 criterion 12 for every registered check: with every accessor on the check's service base class patched to return a non-semantic error result and the context supplying non-empty audit and log-archive account lists, `execute()` yields only ERROR findings, each with an `ActualValue` matching `^\S+ failed: \S+: `, and yields at least one.
5b. THE Contract_Tests SHALL assert, by AST inspection of every `sra_*` module, that no check module contains an `except` clause inside `execute()` (Requirement 4 criterion 11) and that no check module references `session.client`, `boto3.client`, `boto3.Session`, or `_ctx.get_client` (Requirement 2 criterion 8).
6. THE Contract_Tests SHALL assert that no check module in the Check_Catalog passes an `ActualValue` to `failed()` matching the confessing patterns enumerated in Requirement 4 criterion 7, by AST inspection of every `sra_*` module.
7. THE Contract_Tests SHALL assert, for every Discriminator, that an unrecognized code returns `False`, that a recognized semantic code returns `True` for its declared operation, and that the same code returns `False` for an operation it is not declared for.
8. THE Contract_Tests SHALL assert, for the Availability_Lookup, that an unrecognized service identifier returns `True` and logs at `warning`; that a GovCloud Region is measured against the `aws-us-gov` partition; that a service known to be absent from a Region in the bundled endpoint data (`apprunner` in `us-west-1`) returns `False` for that Region; and that a non-regionalized service (`shield`, `organizations`) returns `True` for every Region rather than `False` for all of them.
9. THE Contract_Tests SHALL require no AWS credentials and SHALL issue no AWS call.
10. THE Contract_Tests SHALL enumerate clients, accessors, and checks by reflection over the service packages and the registry, so that a method or check added later is discovered without a second edit, matching the catalog-wide approach the existing property suite already uses over all 158 checks. For a service base class, the enumeration SHALL be every public method defined in that class's own `vars()` — not a heuristic over method source text, which misses accessors that delegate through a private helper, as `SecurityIncidentResponseCheck.list_memberships` does through `_discover_memberships` — and the adapter table for the base SHALL classify every one of them as an accessor (driven through Properties 7–9), a pure helper over a success dict (asserted never to touch the context), or the discriminator table, so that a method with no classification fails. The adapter tables of criteria 4a and 5 are fixture data, not the enumeration; the reflection-equality assertion is what stops them from becoming a maintained allowlist.
10a. WHERE a Contract_Test is expected to fail until its target is migrated, THE Contract_Tests SHALL mark it `xfail(strict=True)` keyed on the individual adapter — one `(service, method)` pair — and not on the service, because `macie` and `waf` each already hold one conforming method beside many non-conforming ones, and a service-level mark would produce a strict XPASS on the conforming method while an unmarked service would fail on its siblings. The pending set SHALL shrink to empty by Phase 7 and SHALL then be deleted with its hook; a stale entry is itself a failure.
11. WHERE a Service_Client method or Base_Accessor is exercised by the Contract_Tests, THE Contract_Tests SHALL name the service and method in the test identifier, so that a failure identifies the offending method without reading the assertion.
12. THE Contract_Tests for a service SHALL land in the same change as that service's migration and SHALL NOT be marked optional in the task list, because the two preceding specs left 15 and 17 optional test tasks unchecked respectively and this feature's test surface is larger than either.

### Requirement 8: The library never writes to stdout

**User Story:** As the maintainer of the MCP server, I want the scanner library to emit nothing on stdout, so that a diagnostic added to a client or base class cannot corrupt the JSON-RPC transport that shares the stream.

#### Acceptance Criteria

1. THE Stdout_Contract SHALL require every diagnostic emitted by a library module to go through the `sraverify` logger from `core/logging.py`, including the three this feature introduces: the `call_aws` failure log, the Availability_Lookup's unknown-service `warning`, and the `ScanContext._set` backstop's `warning`.
2. THE Stdout_Contract SHALL prohibit any call to `print()` in a library module, and SHALL prohibit any write to `sys.stdout` or `sys.__stdout__` by name, because a `print()` that reaches the Library_Entry_Point is the one defect on this list that no logger configuration can contain.
3. THE Stdout_Contract SHALL prohibit `warnings.warn()` in a library module, because the MCP server has to suppress the `warnings` module globally to keep its stderr readable and a library that relies on that suppression is depending on its caller's configuration; the `sraverify` logger at `warning` level is the replacement.
4. WHEN the Library_Entry_Point runs to completion over a catalog whose checks yield PASS, FAIL, and ERROR rows, including a check whose client returns an error result and a check that raises into the Scan_Orchestrator's guard, THE Library_Entry_Point SHALL write zero bytes to `sys.stdout`.
5. WHEN the Library_Entry_Point raises `UnknownCheckError` or `NoChecksSelectedError` before any AWS call, THE Library_Entry_Point SHALL have written zero bytes to `sys.stdout` before raising, so that a usage error surfaced through the MCP server is reported by the exception alone.
6. THE Contract_Tests SHALL assert criterion 4 dynamically, by replacing `sys.stdout` with a stream whose `write` raises, running the Library_Entry_Point over the existing three-probe isolated catalog, and requiring that it completes and returns its findings; a `print()` anywhere on the path fails the test at the call site with a traceback naming it.
7. THE Contract_Tests SHALL assert criteria 2 and 3 statically, by an AST walk of every library module that rejects any `Call` whose function is the name `print`, any `Attribute` access of `stdout` or `__stdout__` on the name `sys`, and any `Call` to `warnings.warn`, so that the dynamic test's coverage gap — a `print()` on a branch the three-probe catalog does not reach — is closed by the static one.
8. THE Contract_Tests SHALL assert that `core/logging.py` leaves the root logger with exactly one handler, that handler's stream is `sys.stderr`, and the `sraverify` logger's handlers all write to `sys.stderr`, so that a future edit which adds a `StreamHandler()` with its default stream (which is stderr today, but is a default rather than a declaration) is caught if the default is ever overridden.
9. THE Stdout_Contract SHALL be recorded in `tech.md`'s Logging section and in `creating_checks_best_practices.md`'s Logging section as an enforced rule with a pointer to the tests, replacing the current "Never call `print()` from library or check code" convention, so that the next author reads a contract rather than advice.
